AI-DLC / TEAM CASE
チーム1週間流れ基礎資料
A CONCRETE 3-PERSON SCENARIO

3人で、AI-DLCを
どう使うか。

「社内備品予約アプリ」を、企画担当・開発担当・品質／運用担当の3人で1週間試作するケースです。AIは4人目のように振る舞いますが、承認者にはなりません。

01 / TEAM DESIGN

まず、責任の境界を決める

少人数チームでは、1人が複数の役割を持ちます。大切なのは肩書きではなく、各成果物の「作成・レビュー・承認」が誰にあるかを曖昧にしないことです。

佐藤：プロダクト担当

目的と優先順位の責任者
  • 利用者へのヒアリング
  • 要件・受入条件の承認
  • スコープと優先順位の決定
  • AIへの入力情報を提供

鈴木：開発担当

設計と実装の責任者
  • 技術選定とアーキテクチャ
  • AI生成コードの統合
  • 単体テストとCIの整備
  • 変更差分の説明

田中：品質・運用担当

検証とリリース判断の責任者
  • テスト計画とリスク確認
  • セキュリティ観点のレビュー
  • ログ・監視・ロールバック設計
  • リリース可否の承認
AIの扱い： AIは調査員、設計レビュアー、実装補助、テスト作成者として使います。チャットの回答を正式な決定にせず、必ずリポジトリ内の仕様書・Issue・レビュー記録に落とします。
02 / ONE-WEEK SPRINT

1週間の進行例

毎日、短い同期時間を設けます。AIとの作業は個別に進めても、成果物と判断だけはチームで共有します。

月曜
Inception
課題と成功条件を定義
佐藤がヒアリング結果を提示。AIにユーザーストーリー、未確定事項、受入条件の候補を整理させ、3人でMVP範囲を承認します。
成果物：product-brief.md成果物：決定ログ
火曜
Inception
設計を小さく確定
鈴木が既存構成を説明し、AIにAPI・DB設計の選択肢を比較させます。田中は認証、権限、個人情報、障害時の観点をレビューします。
成果物：design.md成果物：リスク一覧
水曜
Construction
縦切りで最小機能を実装
「備品一覧を表示する」など、動く単位でIssueを分割。鈴木がAIに実装案を出させ、ローカルで実行・修正し、プルリクエストを作成します。
成果物：PR #1成果物：テスト
木曜
Construction
予約機能とレビュー
AIに境界値・競合予約・権限エラーのテストケースを追加させます。田中は生成テストを鵜呑みにせず、要件との対応を確認します。
成果物：PR #2成果物：テスト結果
金曜
Operations
試験導入と振り返り
少人数へデプロイし、利用状況とエラーを観測。AIにログの傾向を要約させ、3人で「継続・修正・中止」を判断して次スプリントへ戻します。
成果物：運用メモ成果物：次のIssue
03 / WORKING LOOP

1つのIssueを回す流れ

AI-DLCでは、プロンプトを工夫するだけでなく、AIの出力を検証可能な工程に接続します。例えば「備品を予約する」機能は次のように進めます。

1. 意図を渡すユーザーストーリー、制約、完了条件を入力する。
2. 案を出すAIにAPI、DB、画面、テストの案を分けて作らせる。
3. 人間が選ぶチームがトレードオフを確認し、採用案を決定する。
4. 検証するCI、レビュー、手動確認、ログで完了条件を確かめる。
# AIへの依頼例：実装前の設計レビュー
次のIssueを実装可能な単位へ分解してください。

目的：利用者が備品を1件予約できる
制約：同じ備品の時間帯重複を許可しない。未ログインは予約不可。
既存構成：TypeScript / REST API / PostgreSQL

出力：
1. 不足している前提と確認質問
2. APIとDB変更の案
3. 正常系・異常系・境界値テスト
4. セキュリティ上の注意点
5. 実装の順序

コードはまだ書かず、設計上のリスクを優先して説明してください。
04 / ARTIFACTS

残すべき成果物

意図の記録

  • ユーザーストーリー
  • 成功指標と非目標
  • スコープ・制約・未確定事項
  • 採用しなかった案と理由

検証の記録

  • 受入条件とテストの対応表
  • レビューコメントと対応結果
  • CI・セキュリティチェック結果
  • 運用中のメトリクスと判断
実践のコツ： AIに渡したプロンプト、参照したファイル、採用した出力の要点をIssueやPRに残すと、後から再現・修正しやすくなります。
05 / DECISION GATES

承認ポイントを置く

ゲート承認者確認する問いAIに任せない判断
要件確定佐藤誰の、どんな課題を解くのか作る価値と優先順位
設計確定鈴木＋田中制約・障害・変更に耐えるか技術的リスクの受容
PRマージ鈴木＋田中コードとテストが要件を満たすか品質基準の例外
本番導入3人全員戻せるか、観測できるかリリースの最終責任
06 / LESSONS

この例から学べること

速さは分割から生まれる

AIに大きな機能を丸ごと頼むより、意図・設計・実装・検証に分けた方が品質を保ちやすくなります。

成果物がチームをつなぐ

3人全員が同じチャットを読む必要はありません。仕様、差分、テスト結果を共通言語にします。

運用が次の要件になる

リリース後の事実を次のIssueへ戻すことで、AI-DLCは単発の生成ではなく学習する循環になります。
